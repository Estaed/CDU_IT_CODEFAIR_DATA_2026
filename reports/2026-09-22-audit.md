# Crosscheck UI Audit

No files changed. No build, test, or write command was run.

1. **F1 — High — Report saving can silently strand the user**

   **File:** `app/report.js:350-367`

   **Evidence:**

   ```js
   await window.CrosscheckStore.saveReport(line);
   ...
   saveButton.textContent = "Save report";
   ```

   If storage fails, the promise rejects before the report line is rendered and the button remains `"Saving"` and disabled.

   **Smallest fix:** catch the failure, render the generated line anyway, and show: **“Could not save this report on this phone. You can still copy or send this line.”**

2. **F2 — High — Copy controls claim success when copying failed**

   **Files:** `app/app.js:388-406`, `app/report.js:180-200`, `app/report.js:263-266`

   **Evidence:**

   ```js
   document.execCommand("copy");
   ```

   Its return value is ignored, but the UI still changes to `"Copied"`.

   **Smallest fix:** check the result and show **“Copy failed. Select the text and copy it manually.”** when false.

3. **F3 — High — Camera errors expose browser internals**

   **File:** `app/transfer.js:692-696`

   **Evidence:**

   ```js
   const why = error && error.name ? ` (${error.name}, ${location.protocol})` : "";
   counter.textContent = `Could not access the camera${why}.`;
   ```

   A non-technical user may see `Could not access the camera (NotAllowedError, https:).`

   **Smallest fix:** replace with **“We couldn't use the camera. Allow camera access in your browser, then try again.”**

4. **F4 — High — A valid update can be reported as invalid data**

   **File:** `app/transfer.js:610-628`

   **Evidence:**

   ```js
   } catch (error) {
     result = null;
   }
   ...
   : "That did not look like Crosscheck data; try again";
   ```

   Storage failure and malformed data produce the same misleading message.

   **Smallest fix:** distinguish storage failure and show **“The update is valid, but this phone could not save it. Try again.”**

5. **F5 — Medium — Search has no empty state**

   **File:** `app/app.js:703-709`

   **Evidence:**

   ```js
   results.textContent = "";
   ...
   for (const community of pack.communities.filter(...)) {
   ```

   A search with no matches leaves a blank area, so users cannot tell whether searching worked.

   **Smallest fix:** show **“No communities match that search.”**

6. **F6 — High — Tabs lack tab-panel semantics**

   **Files:** `app/index.html:21-25`, `app/app.js:952-980`

   **Evidence:**

   ```html
   <nav class="tabs" role="tablist">
   <a class="tab" role="tab" aria-selected="false" ...>
   ```

   There are no `aria-controls`, matching `tabpanel` elements, or panel IDs. These are route links, not actual tabs.

   **Smallest fix:** remove `role="tablist"`/`role="tab"` and use navigation links with `aria-current`.

7. **F7 — High — Map points are focusable but not accessible controls**

   **File:** `app/app.js:1643-1695`, `app/app.js:1764-1769`

   **Evidence:**

   ```js
   tabindex: "0",
   ...
   role: "img",
   "aria-label": `Map of the Northern Territory, ${pack.count} communities`,
   ```

   The points have keyboard handlers but no role or accessible name. The parent SVG is an image, which may hide the interactive points from assistive technology.

   **Smallest fix:** give each point `role="link"` and an `aria-label` such as **“Wadeye, priority 12, open community”**.

8. **F8 — Medium — Priority, Map and Share screens have no page heading**

   **Files:** `app/app.js:1784-1806`, `app/app.js:1874-1880`, `app/app.js:1990-2035`

   **Evidence:** these render directly into `<main>` without an `h1`; Priority begins with a `<p>`, Map with the lens control, and Share with a `<div>`.

   Screen-reader users lose the page context when navigating between routes.

   **Smallest fix:** add headings: **“What to fix first”**, **“Map”**, and **“Share”**.

9. **F9 — Medium — Report status and carrier controls are unlabeled groups**

   **File:** `app/report.js:302-324`, `app/report.js:373-376`

   **Evidence:**

   ```js
   const statusRow = el("div", ...);
   const carrierRow = el("div", ...);
   ...
   "What is your phone doing here?"
   ```

   A screen reader cannot reliably tell which buttons are status choices and which are carrier choices. The carrier is also not identified as optional.

   **Smallest fix:** use fieldsets with legends **“Status”** and **“Carrier (optional)”**.

10. **Medium — Several interactive targets are only 28 CSS px high**

    **Files:** `design/screens/screens.css:23`, `app/app.css:186-190`, `app/report.js:322-325`

    **Evidence:**

    ```css
    .offline-chip, .chip { height: var(--size-chip); }
    ```

    `--size-chip` is 28px. This affects region chips, priority filters, map layer toggles, carrier choices and Reset view.

    **Smallest fix:** give interactive chips and Reset view `min-height: var(--size-touch)`.

11. **Medium — Map labels still overlap at phone width**

    **Files:** `app/app.js:1298-1310`, `app/app.js:1360-1387`

    **Evidence:** the supplied `reports/shots/2026-09-22-map-v3-emulator.png` shows labels such as `Alice Springs`/`Areyonga` and northern labels colliding despite the three-attempt adjustment in `alignLabel`.

    This makes the map’s place names and selected communities ambiguous.

    **Smallest fix:** hide lower-priority labels when collision resolution fails, keeping the selected label and town labels visible.

12. **Medium — “Sources” lens does not explain what sources agree about**

13. **Medium — The same services have two different names**
